A downstream issue, in another repository, that adopts this epic's release handed back to you: its report is the 📨 comment on the epic, in your files, and names it as `<repo>#<number>`. Read the report against the downstream issue's thread, and its pull request if it has one: what it found, where its spec or plan stands, what it asks. Answer its questions from the family's design, its rulings and the code, and send the answer back with `message` and that issue's `repo` and `number`. If its spec is ready and agrees the plan you have talked through, read it, then `approve_spec` with its `repo`: its pull request opens. If it says the plan on its pull request is ready, read that plan, then `approve_plan` with its `repo` when it builds the upgrade the epic needs. A question that needs work in this family is a sub-issue to `file`; one that needs a new rc is a `prerelease` once that work merges. Every action wakes another turn, so never message only to acknowledge. Say on the epic what you make of it, then return what's next in `actions`; leave them empty when there is nothing to do.
