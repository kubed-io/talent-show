This issue adopts a release of an upstream library: the epic it comes from is linked in the issue, beside its hidden `<!-- upstream: … -->` marker, with the rc version, the release it is a candidate for, and the epic's summary of what it brings. This is a fresh thread, not a copy of the epic's: read the epic, its family's pull request if one is open, and the library's changelog for what changed. Then read this repository against it: where it uses the library, what the rc changes for that code, its tests and its docs, and every file that pins the package (`pyproject.toml`, lock files, requirements, CI). Work against the rc as published. Pin it by name, as pip needs for a pre-release, e.g. `>=0.2.0rc1,<0.3`; the floor moves to the final when it ships. Never install from git, in CI or in any pyproject file. Your questions about the release go to the epic in `report`, never to Dr K: n8n posts it on the epic and wakes its agent, whose answer comes back here. Write the plan of the upgrade in this conversation and agree it with the epic before it approves the spec: say in your `report` when your spec is ready and what the plan is. Link the epic in every commit message you write and in what the pull request will say. Dr K's word on this issue wins over the epic's: where they differ, follow his and say so.
