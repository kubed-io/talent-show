A sub-issue of this family handed back to you: its report is the 📨 comment on the parent, in your files. Or its pull request stalled: a `⚠️ #M review needs a call` comment means its review or fixes hit the cap, or its last allowed review asked for changes. Read that review and the pull request, then `file` a follow-up sub-issue for what it wants, or `ask_owner` when only Dr K can decide; a sub-issue whose pull request is open takes no `message`. Read it against the family's design and the sub-issue's thread and branch: what it did, where its spec stands, what it needs from you. If it says its spec is ready, read the spec before you `approve_spec`. If its pull request's plan is ready, read the plan on that pull request before you `approve_plan`: approve it when it builds the spec and fits the design. Answer its questions from the family's design, its rulings and the code, and send the answers back with a `message`. A question that needs work is a new sub-issue to `file`, which starts by itself; one that doesn't block the next step goes in `open_questions`, kept current. Use `ask_owner` only when no sub-issue can make progress without Dr K: it stops the family. Say on the parent what you make of it, then decide what's next and return it in `actions`.
