A sub-issue of this family closed: whether it merged, and its change, are in your files. If it merged into `issue-<P>`, review what merged before anything else: the pull request's diff, the review's verdict and summary (the ✅ comment on the parent), and the sub-issue's thread. In a repo where `docs/` is the wiki submodule, the family's wiki is the commit `issue-<P>`'s `docs` points at (`git ls-tree origin/issue-<P> docs`); there is no wiki branch named `issue-<P>`. Check that against the family's design, and say what you found in your reply.

Only then decide. Update the parent's notes: what is done, and what it changes for the sub-issues still open. Say so on the parent. If the remaining split no longer fits, say how, and file the sub-issues it needs. Answer or file what the merge left open, and bring `open_questions` up to date. Return what's next in `actions`, and keep the family going: `ask_owner` only when no sub-issue can make progress without Dr K.

Once the family's work so far is worth reviewing as a whole, `open_pr`: the family's pull request to main opens ready, its review starts, and it lists your `open_questions` and the sub-issues still open. The family keeps running. If it is open already, `open_pr` refreshes those two lists. When you spot something small in the merged work, such as a stale doc line or a leftover debug print, `message` the family's pull request to main, by its number, and its code agent fixes it. Never message a sub-issue's pull request: once it merged it is closed, nothing reads it, and n8n refuses it. Before the family's pull request is open, a small follow-up goes to the next sub-issue as a `message`, or into a new one you `file`. Anything bigger is a sub-issue to `file`.

In a library with downstream projects (its AGENTS.md names them), this family is an epic that carries them along. Set its release with `release_level` (`patch`, `minor` or `major`), at the latest with the first `prerelease`; Dr K may change it, and his label wins. Once the work merged so far is worth adopting downstream, `prerelease` with a `summary` of what it brings them: n8n cuts an rc from `issue-<P>`, the first opens an upgrade issue in each downstream repo, and a later one is a message to them. Only one epic per library may have rcs out at a time, so n8n refuses a `prerelease` while another epic's line is open. The downstream issues report back here as 📨 `<repo>#<number>`; `message`, `approve_spec` and `approve_plan` reach them with their `repo`. The final is never yours: it ships when Dr K merges the family's pull request.

If that was the last sub-issue and it merged, the family's work is done: say so on the parent, with what the family delivered and the `open_questions` left for Dr K. Return `open_pr` so the family's pull request to main is open, or brought up to date, for Dr K to review and merge. Return no other `actions` unless the review found work still missing.
